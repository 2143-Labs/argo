pite is not on the office switch. The runbook says office-switch ether1 → pite, but that port is down: the office switch only learns pite's MAC on its 10G uplink, and the router egresses pite's frames on ether8 (to-wifi). It is either on router port 8 or behind a transparent wireless bridge. Worth confirming physically — and the guide should be corrected either way.

Two cameras are wireless. Garage (.1.61) and Side (.1.65) leave through the U7 Lite, while the Front cameras and the NVR are wired. The camera subnet is egress-blocked, so this is a placement fact rather than a security one.

What this shows

Seventy-five IPv4 hosts, and the boundary is one box. Only five addresses exist on the ISP side; everything else is behind the MikroTik. The Verizon router forwards specific ports only, so the MikroTik's dst-nat table is the single place that decides what the internet can reach.

Twenty of the 42 hosts on the switch LAN are client and IoT devices. Phones, TVs, a UPS, presence sensors, AiDot and eufy devices, and five MACs with no hostname at all (.5.53, .5.131, .5.146, .5.172, .5.187). They are DHCP, so they are not a misconfiguration — but they are the part of the network with no owner recorded anywhere.

192.168.6.0/24 exists nowhere as an interface. No router address, no bridge; the router holds a blackhole route for the whole /24 and /32s from BGP. That is why ping to any VIP times out and why an unannounced VIP fails closed instead of ARPing into the void.

The tailnet has drifted. desktop-pjem2ib (183 d), serverkvm (168 d) and desktop-1eg884n (96 d) are still listed. Tailnet membership is the operator plane, so pruned devices also shrink what can reach 192.168.6.0/24 over the subnet route.

How to re-check

# VIPs, ports, announcement policy, node ports
kubectl get svc -A -o json
kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik -o wide

# which node carries each prefix (selected path), and the WAN forwards
mikrotik-connect r '/ip route print terse where dst-address~"192.168.6." and active=yes'
mikrotik-connect r '/ip firewall nat print terse where chain=dstnat'

# listener set on a node
ssh 192.168.5.36 'sudo -n ss -ltnuH | awk "{print \$1, \$5}" | sort -u'

# WireGuard: both ends, then the live flows
mikrotik-connect r '/interface wireguard peers print detail'
kubectl --context 2143prod -n default get deploy wireguard-doks -o yaml
kubectl --context 2143prod -n default get cm home-tunnel-proxy -o yaml
mikrotik-connect r '/ip firewall connection print terse where src-address~"10.99" or dst-address~"10.99"'
