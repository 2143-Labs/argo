IP hiding & self-hosted edge — north star

Owner: John · Adopted 2026-10-16 · Design v5.5 · Implementation: not started · Next step: Phase 0 · Board: task 173 (#48)
Lives in argo/docs/ip-hiding-tech.html. Edit it as decisions land; record changes in the changelog.

We host our own sites, chat, games, mail and media, today on two clusters: the one in the house and a small one at DigitalOcean. This document is the target we are building toward: no backend is ever reachable or identifiable from the internet, and the house least of all. Public traffic arrives at small, disposable edge machines that we own and can move between providers at will. Backends reach out to them; nothing reaches in. No Cloudflare, no single third party that sees or controls our traffic, and every piece that runs on an edge is pinned, signed and deployed through a reviewed, recorded pipeline.

The requirements. Everything below exists to satisfy these. If a later change breaks one, it needs a decision recorded here.

  1. No public DNS record points at a backend, and no backend exposes a service to the internet. The house is the hard line; the DigitalOcean cluster follows the same rule. The only listeners allowed are silent, key-authenticated WireGuard ports (the router's, for the DO link and any keyed peer, and DO's end of that link): they answer nothing without a key. External access to something specific goes through one of the doors into the house, never an ad-hoc port forward.
  2. TCP and UDP both work for every public service.
  3. Edges are fungible and ephemeral. Any edge can be destroyed, replaced, or moved to another provider in minutes. Backend addresses (the home IP is mostly static) never matter to the edges.
  4. The home IP is soft state everywhere outside the house. Anything that needs it learns it from a packet the house sent and holds it in memory only. It is never stored in git, a Secret, DNS, or a firewall rule (where the home IP lives).
  5. Backends are pluggable. One edge fleet serves every backend. Adding a backend is a manifest and a connector, not a new edge design.
  6. Zero trust and auditable, shaped for an eventual SOC 2 Type I: pinned, signed, SBOM'd artifacts; reviewed, gated, recorded changes.
  7. Traffic lands in Kubernetes, not on a machine. No backend node is special. The tailnet (headscale) is the operator plane, and only that.

2. Principles

  1. Edges hold nothing worth stealing and nothing worth keeping. An edge is a pinned image plus one rendered config. Losing it loses nothing.
  2. Replace, don't repair. No shell, no SSH, no in-place upgrades. Changing an edge means rendering a new config and rolling the slot.
  3. Home bootstraps every link that touches the house. Every tunnel is initiated from the house (and every other backend dials out too). The far end learns the address from the handshake; nothing has to be told it in advance.
  4. Backends are interchangeable to the edge. An edge knows "names and ports, and which backend owns each". It knows nothing else about a backend.
  5. Backends are separate trust domains. No backend reaches another through a shared control plane: not the tailnet, not the edges, not DNS, not a shared certificate. The one path between backends is the static, key-pinned DO ↔ home WireGuard link, and its reach is fixed by each side's own firewall.
  6. Kubernetes owns everything durable: the per-app contract, the connectors, DNS publication, the deploy runner. Each backend's GitOps deploys its part like any other workload.
  7. Every running byte has a provenance trail. Built or mirrored by CI, scanned, SBOM'd, signed, verified before deploy, recorded after.
  8. Fail closed. An app whose egress must be masked can't reach the internet directly at all. A missing proxy setting breaks the app; it doesn't leak.
  9. Edges are untrusted transit. TLS ends at the backend. An edge sees ciphertext (plain HTTP on port 80 aside), proxies declared ports only, and never routes IP between its peers.

3. Threat model

Defended against

Internet scanners and opportunistic attackers finding the house or any other backend.

DDoS against a backend: floods hit edges with datacenter bandwidth; backend uplinks carry only tunnel traffic.

A provider outage, ban or price change: slots move to another provider.

A compromised edge: it can see what transits it, but it can't reach anything except connector pods on declared ports, and it holds no long-lived credential beyond its own slot key.

Lateral movement: a compromised edge or tailnet control plane gets no path into a backend, and a compromised backend gets no valid certificate for another. The static DO ↔ home link reaches only the ports each side's firewall allows (trust boundaries).

Supply-chain tampering: unsigned or unknown images never reach an edge or a connector.

Accepted (documented)

An edge sees each backend's IP as the source of its tunnel. Removing that needs a relay hop. See risks.

Our own tailnet devices may connect directly to backend nodes and see their IPs.

Providers can see edge memory and user-data (slot key, TURN secret). That's no more than they can do by controlling the VM.

Volumetric attacks larger than an edge's link take that edge down; DNS steers away from it and we add slots.

Out of scope here

Hardening each cluster itself (identity, segmentation, secrets): security epic #160 for home.

Application-layer abuse (bots, scraping): CrowdSec at Traefik, optionally Anubis behind Traefik.

Content caching at the edge: see Toward a CDN.

4. Architecture

Key properties

  • Fixed slots, fungible machines. Slots s1–s4 each have a WireGuard keypair (in OpenBao) and a name s<N>.edge.2143.me. A VM is a slot because the pipeline gave it that slot's key. Replacing the VM, or moving the slot to another provider, changes only that slot's A record. No backend is reconfigured.
  • Backends initiate. Every connector pod resolves every slot name and dials it. The edge learns the backend's current address from the handshake, so a backend IP change heals on the next keepalive and is configured nowhere.
  • Edges are layer 4, routed by name. Port 443 is routed by TLS SNI without decrypting; port 80 by the HTTP Host header (it is plaintext anyway, and ACME HTTP-01 needs it); every other port belongs to exactly one backend. TCP carries a PROXY v2 header with the real client IP, so per-IP rate limits, CrowdSec and mail checks keep working. UDP is relayed through the tunnel.
  • Media relays live on edges. A TURN relay must advertise an address it owns, so coturn runs on every edge. LiveKit stays at home and is reached only through TURN/TLS.
  • The tailnet moves behind the edges too, and stays an operator plane. headscale is a normal app behind Traefik; DERP and STUN come from derper on the edges. Backends never use it to reach each other (trust boundaries).

Routing and ownership rules

  • Each hostname, wildcard and non-HTTP port is claimed by exactly one backend. The render step fails on a duplicate claim.
  • An exact name beats a wildcard. i.2143.me (do) and au.2143.me (home) coexist with no wildcard claimed by either.
  • Names come from the manifest, not from Gateway listeners. Both clusters hold a *.2143.me certificate today, so listener wildcards are ambiguous by design.
  • Known overlap to resolve in Phase 0: files.john2143.com has an HTTPRoute in both clusters. Public DNS points home today.
  • Health is per (slot, backend). A slot that loses one backend withdraws only that backend's names from its address.

Finding DO after a node replacement is the one real bootstrap problem; the DO node is three days old, so replacements are routine. Options:

  • DO Reserved IP (default): one stable address, reassigned by a small DO-side job to whichever node runs wireguard-doks. The router pins it once. verify that DOKS nodes accept a Reserved IP, its cost, and that replies leave from it.
  • Edge rendezvous (fallback): every edge already sees DO's current address as the source of DO's connector tunnel. Home asks an edge over its own tunnel and updates the router. A lying edge only causes a failed handshake, because the keys are pinned; it needs a scoped RouterOS API user at home.
  • Rejected: a DNS name for the link (publishes a backend address); a DO API token at home (a cross-backend credential).

8. The per-app contract

Each backend has one manifest, kept in that backend's GitOps repo. It is the only thing an app owner edits to publish something or mask its egress. The backend's GitOps renders its connector from it. The edge pipeline renders from the commits pinned in edge-tofu/manifest.lock, so a new port ships backend-first and then edge-side, each as its own reviewed change.

Inbound: MX on the edges

m.2143.me resolves to the live edges like any other name. Ports 25, 587 and 993 pass straight through with PROXY v2, so Stalwart terminates TLS, holds the keys, stores the mail, and sees the real sending server's address for SPF, reputation and rate limits. Without PROXY every message would appear to come from a connector pod and SPF would fail.

Is it bad that the MX lands on a droplet IP? Not for receiving. Address reputation and reverse DNS matter to the sender; servers delivering to us don't score our address. The edge holds no mail and no keys, both providers allow inbound 25, and senders queue and retry for days if an edge is replaced mid-delivery. The real requirements are:

  • MTA-STS in enforce mode plus TLS-RPT for m.2143.me (and DANE if 2143.me is DNSSEC-signed verify). STARTTLS on port 25 is opportunistic; without a policy a hostile edge could strip it and read mail in transit. MTA-STS binds to the MX hostname and certificate, not the IP, so moving edges doesn't affect it.
  • Remove mx from the m.2143.me SPF record before the MX moves. Otherwise every edge IP becomes an authorised sender. Edges never send mail.
  • A droplet IP would be bad as a sending address (shared cloud ranges, outbound 25 blocked). That is the case this design avoids: nothing sends direct-to-MX.

Outbound: through the relay

Recipients see Resend's servers, not ours. Two things to confirm:

  • What the relay sees and stamps. Stalwart connects to Resend from the household WAN IP today. Whether Resend writes that address into a Received header that recipients can read is not documented. Phase 0 sends a test message to an outside mailbox and reads the raw headers. verify
  • If it leaks: send Stalwart's relay connection through masked egress. Both providers block common SMTP ports outbound (Hetzner 25/465, DigitalOcean 25/465/587); Resend also listens on 2465 and 2587, which neither blocks. Stalwart has no HTTP CONNECT support, so this would be a tunnel-level egress path rather than tinyproxy, and gets designed only if the header check fails.
  • Stalwart's own Received line for mail submitted by our clients records the client's address. That is expected and does not reveal a backend.

16. Toward a CDN (future, not committed)

Today the edges are proxies, not a CDN: they cache nothing because they never see plaintext. Becoming our own CDN for static, public content (the image hosts, site assets) means letting an edge terminate TLS for specific hostnames and cache their responses.

GainCost
Static content served from the edge; backend uplinks carry only cache missesThat hostname's certificate and plaintext live on an untrusted, ephemeral machine
Floods against cached content never reach a backendCache invalidation, per-edge certificate issuance, a bigger edge image to sign and audit

If we do it: opt in per hostname in the manifest (cache: true), short-lived certificates issued in the backend and rendered per slot, public content only, never anything behind a login. That would be a new decision recorded here first.
